# Deploying the WordPress store to cPanel (hosting.com)

What [`.cpanel.yml`](.cpanel.yml) does and — just as importantly — what it does not
do. Read the "What git deploys" section before you start, because the mental model
is the part that trips people up.

## What git deploys, and what it doesn't

cPanel's Git deployment copies **files only**. It never touches a database, never
runs `composer`/`npm`, and cannot install plugins.

| Thing | How it gets to production |
|---|---|
| `vitalis` theme (17 files) | **Git deploy** — `.cpanel.yml` |
| WordPress core | cPanel's WordPress installer (server-owned) |
| WooCommerce | Installed on the server, once |
| `wp-config.php` (DB creds, salts) | Generated by the installer. **Never in git** |
| Products, prices, images, gateway settings, gate password | Database — `docker/setup.sh` or wp-admin |

`.cpanel.yml` deliberately does **not** deploy this repo's `wordpress/` directory.
That's a reference copy of core; overwriting the server's core from git breaks
WordPress auto-updates and can leave a half-updated install. The clone in
`~/repositories/` holds the whole repo, but only the theme is copied into the
docroot — nothing else in the repo is web-accessible.

cPanel forbids wildcards in deployment tasks, so all 17 theme files are listed
individually. **When you add a theme file, add a `/bin/cp` line for it** or it
silently won't deploy.

## One-time setup

### 1. Push `.cpanel.yml` to GitHub

It must be committed at the repo root, on the branch you deploy.

```bash
git add .cpanel.yml DEPLOY-CPANEL.md docker/setup.sh
git commit -m "Add cPanel git deployment for the vitalis theme"
git push origin main
```

### 2. Install WordPress on the server first

In cPanel, use **WordPress Toolkit** or **Softaculous / WordPress Manager**
(hosting.com's exact label varies by plan) to install WordPress into the docroot
you want — `public_html` for the main domain.

Do this *before* deploying, so `wp-config.php` and core exist and the theme has
somewhere to land.

Then install and activate **WooCommerce** from **wp-admin → Plugins → Add New**.
It is not in this repo.

### 3. Create the cPanel repository

**cPanel → Files → Git™ Version Control → Create**

- Toggle **Clone a Repository** on
- **Clone URL:** `https://github.com/JDStephens31/Vitalis-Labs.git`
- **Repository Path:** `repositories/Vitalis-Labs` (must be outside the docroot)
- **Branch:** `main`

If the GitHub repo is private, HTTPS cloning won't work unattended — copy the
public key from cPanel's SSH Access page into GitHub as a deploy key and clone via
`git@github.com:JDStephens31/Vitalis-Labs.git` instead.

### 4. Deploy

On the repository's **Pull or Deploy** tab: **Update from Remote**, then
**Deploy HEAD Commit**. Deployment requires a clean working tree on the server
side, so never edit theme files directly in `~/repositories/`.

Then **wp-admin → Appearance → Themes → activate Vitalis**.

### 5. Populate the store

Two options. Prefer the script if you have SSH.

**With SSH + WP-CLI** (check whether your plan includes both):

```bash
cd ~/repositories/Vitalis-Labs
WP_PATH=$HOME/public_html \
SEED_DIR=$HOME/repositories/Vitalis-Labs/assets \
WP_URL=https://your-domain.com \
sh docker/setup.sh
```

This installs WooCommerce, sets the US/USD store config, enables the offline
gateways, imports the vial images, and creates all four products with their
display meta. It's idempotent — safe to re-run. Since WordPress is already
installed by cPanel it skips `core install`, so your existing admin user and URL
are left alone.

**Without SSH**, do it by hand in wp-admin: create the four products
(`VL-BPC-10` $100, `VL-GHK-100` $100, `VL-RETA-10` $100, `VL-RETA-30` $200, stock
25 each), upload the images from `assets/`, and set the per-product custom fields
`_vitalis_cap`, `_vitalis_dose`, `_vitalis_purity`, `_vitalis_sub` — the catalog
card reads these for the dose badge, purity line, and cap glow. Values are in
[`docker/setup.sh`](docker/setup.sh) under "Setting catalog display meta".

## Production configuration

These are the things that differ from local, and none are handled by git.

### Email — needs attention

[`inc/mail.php`](wordpress/wp-content/themes/vitalis/inc/mail.php) routes mail via
SMTP using `VITALIS_SMTP_*` constants that **only exist in Docker**, injected by
`docker-compose.yml`'s `WORDPRESS_CONFIG_EXTRA`. On cPanel they're undefined, so
the SMTP hook returns early and WordPress falls back to the server's `sendmail` —
which does work, but the From address becomes `wordpress@your-domain.com`.

To send as a real address, add to `wp-config.php` above
`/* That's all, stop editing! */`:

```php
define( 'VITALIS_MAIL_FROM',      'orders@vitalislabs.com' );
define( 'VITALIS_MAIL_FROM_NAME', 'Vitalis Labs' );
```

For an external SMTP provider, also define `VITALIS_SMTP_HOST`, `VITALIS_SMTP_PORT`,
`VITALIS_SMTP_USER`, `VITALIS_SMTP_PASS`, and `VITALIS_SMTP_SECURE` (`'tls'` or
`'ssl'`). Do not deploy the Mailpit container — it's local-only.

Order emails matter here: Venmo is a manual gateway, so the payment-instructions
email *is* the checkout. Place a test order and confirm it arrives.

### Change the gate password

[`inc/gate.php`](wordpress/wp-content/themes/vitalis/inc/gate.php) seeds the shared
site password to `V1T4L1S` on first load. Change it at **wp-admin → Settings →
Vitalis Gate**. It's stored only as a bcrypt hash; rotating it invalidates every
unlock cookie.

### Check these too

- **Permalinks** — Settings → Permalinks → Post name. The gate and WooCommerce
  both assume pretty permalinks.
- **WooCommerce "Coming soon"** — newer versions default this ON and hide the whole
  shop. `setup.sh` turns it off; verify manually if you skipped it.
- **Venmo gateway** — WooCommerce → Settings → Payments → Venmo. Defaults are the
  real `@Vitalislabs` handle and payment link, but confirm them, and set the QR
  code image URL (empty by default).
- **`WP_DEBUG`** — Docker sets it on. Make sure it's `false` in production
  `wp-config.php`; `debug.log` under `wp-content/` is publicly readable.
- **HTTPS** — issue an AutoSSL/Let's Encrypt cert and confirm the WordPress Address
  and Site Address use `https://`. The gate cookie should only travel over TLS.

## Updating the theme later

```bash
# edit files under wordpress/wp-content/themes/vitalis/
git commit -am "Theme tweak"
git push origin main
```

Then **Update from Remote** → **Deploy HEAD Commit** in cPanel.

Pushing to GitHub does not auto-deploy — GitHub is the origin, cPanel pulls from
it. Auto-deploy on push only happens when you push *directly* to the cPanel-hosted
repo, which you could add as a second remote:

```bash
git remote add cpanel ssh://user@your-domain.com/home/user/repositories/Vitalis-Labs
git push cpanel main   # this one triggers deployment via post-receive hook
```

## The static site is unaffected

This repo also contains the static Supabase storefront ([`index.html`](index.html),
[`support.js`](support.js), [`doc-page.js`](doc-page.js)). It is still live and is
**not** deployed by this config. Both storefronts cannot share one docroot —
Apache would serve `index.php` or `index.html`, not both. If you later want the
static site on the same account, give it its own subdomain and a separate set of
`/bin/cp` tasks pointing at that docroot.
